LM boss 的机制会随 `IAnimatedMiniBossServant` 一并继承给仆从。**用户要求这些机制彻底删除（"不是关掉 而是删掉"），别以"严格对齐原版"为名加回来。**

`IAnimatedMiniBossServant` 只有两个子类：`CloudGolemServant`、`OvergrownColossusServant`，所以直接删在父类，两个一起生效。2026-09-24 已删：

| 机制 | 删掉的东西 |
|---|---|
| 高低差保护 | `IAnimatedMiniBossServant.hurt()` 里的 `isTargetCheesing(-4,4)`、`CloudGolemServant.isTargetCheesingBoss()` 及其调用、`IAnimatedMonsterServant.isTargetCheesing()` 定义 |
| 脱战回血 | 父类 `regainHealthWithoutTarget()` 及其 tick 调用、两个子类的覆写、`TICKS_WITHOUT_TARGET`/`ticksWithoutTarget` |
| 归位传送 | 父类 tick 里整套 `inActiveTicks`/`return_to_spawn_ticks` 逻辑、`SPAWN_POS` 同步数据 + NBT posX/Y/Z + `get/setSpawnBlockPos` + `moveToBlockPos` + 只用来记出生点的 `finalizeSpawn` 覆写 |
| 阶段重置 | `CloudGolemServant.tick()` 顶部那段（无目标 60 tick + 裂痕 LOW/NONE → `setTextureVariant(0)`）。**`setTextureVariant(0)` 全文件仅此一处**，删掉后云傀儡打完大招会永久停在贴图 1（`isAngry()` 恒 true，招式池跟着变）；用户决定改用**喂食大气符文回到一阶段**的交互来替代。已在 `CloudGolemServant.mobInteract()` 实现（主人 + `isAngry()` + `itemstack.is(ModItems.AIR_RUNE.get())` → 扣 1 + `setTextureVariant(0)` + `attackLock = 0` + 音效/HEART 粒子），模板抄 `OvergrownColossusServant.mobInteract`。**喂食同时 `setHealth(getMaxHealth())` 回满血**——这是让"回一阶段"真正留住的手段（回满 → Crackiness 必为 NONE → 下面①的自动暴走条件不成立），用户 2026-09-24 选的方案，别再加"已喂食"标记/计时器。两个原生约束：①自动暴走只看 `getCrackiness() == Crackiness.MEDIUM`，而本文件的 `Crackiness` 档位是 NONE≥75%/LOW≥65%/MEDIUM≥25%/HIGH<25%（`byFraction` 升序遍历取首个 `fraction < 阈值`）→ **只有血量落在 [25%,65%) 这一档会 tick 把 `attackLock` 置 1 → `attackState 21` → 25 tick 后 `setTextureVariant(1)` 回二阶段**；≥65% 和 <25% 本来都不触发，喂食在那两档能留住，只有 25%~65% 会「刚喂完就变回去」。`attackLock = 1` 全文件仅此一处写入；②`BREAK>=3` 的破碎态 tick 每帧强制贴图 2/3，喂食只改招式池不改贴图。大气符文 = LM `ModItems.AIR_RUNE`（2.2.3 已核对 lang `item.legendary_monsters.air_rune` = 大气符文） |

**阶段重置删掉的可见后果（2026-09-30 用户问过）**：这一条不只影响云傀儡。LM `PosessedPaladinEntity:385` 也有一段同类逻辑（`ticksWithoutTarget == 0 && getTarget() == null && ModConfig.MOB_CONFIG.canBossesResetPhases && getIsSecondPhase() && 裂痕 NONE/LOW` → 回一阶段），**我们没移植**。所以堕落圣骑士仆从一旦进二阶段就**永久红**（红灵魂剑/红匕首/红三叉戟/红粒子），不会再像原版那样脱战变回来。用户 2026-09-30 明确选择**不动**（保持现状）。别把这当成"红色弹射物是 bug"再查一遍——分清哪些红是原版，见 [[lm-red-projectile-sources]]。

**2026-09-30 补：圣骑仆从也走了云傀儡那条"喂食回一阶段"的路**（用户："给圣骑仆从二阶段加一个喂食堕落之魂回到一阶段满血"）。`PossessedPaladinServant.tryRevertToFirstPhase()` 原本（7488dbe7 移植时就带着，**不是 LM 原版**——2.2.3 的 `ModItems`/实体里 `METAL_DEBRIS` 只被合成表引用，没有实体用它）判据是 `ModItems.METAL_DEBRIS` 且带 `getHealth() < getMaxHealth() → return false`（等于**要求已满血**，所以它只能"回阶段"不能"回血"，形同废设）。用户 2026-09-30 选择**用堕落之魂替换掉它**（不是两条并存）：物品判据改 `ModItems.CORRUPTED_SOUL`、删掉满血前置、`setPhase(1)` 后补 `setHealth(getMaxHealth())`，其余音效/SOUL 粒子环保留。现在金属残骸在这个仆从身上**没有任何用途**了。要点：①`tryAwaken()` 排在前且只在 `attackState == 34`（沉睡）生效，而本仆从的入眠只发生在 `finalizeSpawn`（MOB_SUMMONED，必为 phase 1）和 NBT 读档，所以二阶段醒着时堕落之魂不会被唤醒那条截胡；②保留 `getAttackState() != 0` 前置是必须的——`PossessedPaladinSecondPhaseGoal` 在 `attackState 26` 的第 49 tick 才 `setPhase(2)`，动画中喂食会被它覆盖回去；③回满血 → `getCrackiness()` 为 NONE → `shouldEnterSecondPhase()`（要 MEDIUM/HIGH）不成立，不会当场变回去，与云傀儡同款留人手段，别再加标记/计时器。（本条只讲阶段回退，不要外推到"仆从统一火免"之类，见本文件下方注册项取舍。）

父类里**保留**的：`REDUCED_DAMAGE_TICKS`/`reducedDamageTicks`（伤害减免冷却，tick() 里只剩这一行）、`lastTargetPos`/`saveTargetPos`、`damageCap`/`damageReduction`/`canApplyMobEffect`。

另：云傀儡休眠改为**待命才休眠**（用户要求）——`isStandby()` = `isStaying() && !isCommanded() && getTarget() == null`（"待命"=Stay 模式且无目标，见 [[goety-servant-follow-standby]]，别用 `!isFollowing()`）；tick 在 `super.tick()` 前入眠、之后判醒（后置是让 `IAttackGoal(1,2,...,8.0F)` 先接手播苏醒动画）；`onSyncedDataUpdated` case 0 的 guard 补了 `&& !sleepAnimationState.isStarted()` 兜底直接唤醒的动画残留。

入睡/苏醒（2026-09-25 现状）：**当 tick 入眠 + 自造 0.75s 倒下过渡**。`CloudGolemAnimations.sleep` 是 `withLength(0)` 的瞬时姿势，其关键帧逐通道等于 `awake` 的 t=0 姿势（已数值核对：body 17.5°/-9、rune_lower y-1、rune_upper y-5、双臂位移、leftleg 42.5、rightleg z-3；`awake` len 1.0、关键帧 0/0.75、t=0.75 全零），所以 `reverse(awake)` 的倒下过渡能严丝合缝接到 `sleep` 静态姿势上。tick 里待命条件满足的**当 tick** 就 `setSleep(true)`（`SLEEP_STANDBY_DELAY = 20` 等待计数是用户认定的延迟，已删）。苏醒路径：`super.tick()` 之后 `状态1 && !isStandby()` → `setAttackState(2)`（`awake` 动画），`AWAKE_TICKS = 20` 后 `setSleep(false)` 回 0；**状态 2 原来只有 `IAttackGoal(1,2,...,8.0F)`（8 格内有目标）能进**，现在两条路并存：goal 在同 tick 先抢 `start()`，没目标时（玩家点跟随）才落到 tick 里那段；两条路都以 20 tick 收尾。状态 2 仍算 `isSleep()`（只影响 `getattackstate == 0` 的攻击 goal 不启用）。**2026-09-25 用户要求"不再有无敌和一直睡眠，对齐红石巨兽"：两个仆从 `hurt()` 里的 `isSleep()` 免伤子句已删**（LM 原版是有这条的，属用户明确要求的偏离）——删掉后挨打才会走完 `LivingEntity.hurt` → 置 `lastHurtByMob` → Goety `ServantHurtByTargetGoal`（`Summoned.registerGoals` 的 targetSelector 1）→ `getTarget() != null` → `isStandby()` 假 → 既有唤醒链；此前免伤挡住 `super.hurt`，目标永远拿不到，"一直睡眠"就是这么来的。同时删掉湮灭猎影的 `canBeSeenAsEnemy() = !isSleep() && super`（`TargetingConditions.test` 在 attacker 为空时、以及 `LivingEntity.canAttack(LivingEntity)` 都读它 → 睡眠时任何 mob 都不会选它当目标，等于另一种无敌）。**留着没动的**：湮灭猎影 `addEffect()` 睡眠时返 false（LM 原版）、`isDuringTeleportation()` 闪避无敌（LM 原版）、云傀儡 `GolemInvulnerabilityTime`（LM 原版，受 LM 自己的 `ModConfig.MOB_CONFIG.CloudGolemInvulnerabilityTime` 开关控制）。注意 Goety 的 `Summoned` 不会因挨打清 staying（只置 `NoHealTime`），所以**主人自己打不会唤醒**（`ServantHurtByTargetGoal` 排除主人）——这和坐着的红石巨兽一致。入眠条件是 `isStandby() && attackState == 0 && attackLock == 0`——**`attackLock` 那一条意味着裂痕 MEDIUM（血量 25%~65%）的傀儡不会睡**，得先喂大气符文回一阶段。

模型是**每个渲染器一个单例**（多只云傀儡共用），任何跨帧状态都得从实体自己的 `AnimationState` 现算，不能存在模型字段里（[[forge-pose-blend-weight-invariants]]）。

**tick 唤醒路曾被 hold goal 的 `stop()` 打回（2026-09-25 查证并已修）**：`GoalSelector.tick()` 顺序是「cleanup 停掉 `canContinueToUse()` 为假的 → goalUpdate 抢 flag/start」；`WrappedGoal.canBeReplacedBy` 只要求候选 priority 更小，所以优先级 0 的 `IAttackGoal(1→2)` 在**同一 tick 内**先 `stop()` 掉优先级 1 的 hold goal、再 `start()` —— `IStateGoal.stop()` 写的 `attackendstate`(0) 被后写的 `setAttackState(2)` 覆盖，**goal 唤醒路一直是正常的**。但 tick 唤醒路（无目标 / 目标 >7 格 / 玩家点跟随 / 湮灭猎影的 7→…）没有 goal 参与：`setAttackState(2)` 之后下一 tick cleanup 发现 hold goal 的 `canContinueToUse()`（`attackfinaltick = 0` 时退化成 `canUse()` = `getAttackState() == getattackstate`）为假 → `stop()` → `setAttackState(0)`，苏醒动画只播 1 tick 就被 `onSyncedDataUpdated` case 0 的 `stopAllAnimationStates()` 掐掉，外壳"啪"一下弹开。**修法（已落地，四个仆从统一）：hold goal 匿名子类覆写 `canContinueToUse()` 把苏醒状态一起算进去**——`AnnihilationPursuerServant` 早就写着 `== 6 || == 7`（就是给同一个坑打的补丁，别当冗余删），2026-09-25 给 `CloudGolemServant`/`OvergrownColossusServant`/`ShulkerMimicServant` 补上 `== 1 || == 2`。副作用是好的：hold goal 在醒来那几十 tick 内继续持有 MOVE/LOOK/JUMP 并清零横向速度，于是 tick 路和 goal 路行为一致（都定身演完再动），状态回 0 时它自己因 canContinueToUse 为假而 stop。**同一个坑的第二半也已修**：`die()` 把状态置成死亡态（云傀儡/巨像 8、湮灭猎影 17、壳灵 13）后，hold goal 下一 tick 仍然会 `stop()` → 无条件写 `attackendstate`(0) → case 0 的 `stopAllAnimationStates()` 把刚起步的死亡动画掐掉（四个全中）；修法是 hold goal 匿名子类再覆写 `stop()`，**只在状态仍等于自己那个 getattackstate 时才 `super.stop()`**（云傀儡/巨像/壳灵判 `== 1`，湮灭猎影判 `== 6`）——别的代码已经把状态换成下一个（2 或死亡态）时就不写。唯一被保留下来的写入场景是"状态仍是 1 却被强制停"（flag 被 `disabledFlags` 停掉，例如 Mob 乘客接管），那时写 0 正是想要的（强制唤醒）。`getattackstate`/`attackstate` 在 `IStateGoal` 里是 private，匿名子类只能用 `entity`/`attackendstate`/`attackseetick`，所以这里只能硬写字面量。

死亡返还：`CloudGolemServant.die()` 也照 `OvergrownColossusServant.die()` 的 `FlyingItem` 模式退还 `ModItems.AIR_RUNE`（`!isClientSide && getTrueOwner() != null` → 建 FlyingItem 设 owner/item/`ParticleTypes.HAPPY_VILLAGER`/`ItemConfig.ReviveSecondsCool` → `addFreshEntity` → 再 `setAttackState(8)` + `super.die(source)`）。返还物用飞物而非 `spawnAtLocation`，与自然水晶同款。`DiedOnce` 字段在云傀儡里只做 NBT 存取、无逻辑。

注册项取舍（**不是漏改，别对着 LM 的 `ModEntities` 当 bug 删**）：`LmEntityRegistry.CLOUD_GOLEM_SERVANT` 的 `.fireImmune()` 是**有意补偿**——LM 原版云傀儡二阶段会下雨所以不怕着火，仆从版不带天气机制，用火免补上（用户 2026-09-25 明确）。LM `ModEntities` 里 `cloud_golem` 确实没有 `fireImmune()`，对照表会显示成"我们多加了"，那是假象。**这条只适用于云傀儡，别外推**——同一批注册项里 9 个有 7 个是原样照搬 LM（含 LM 自己带火免的 6 个），所以本仓库没有"仆从统一火免"的惯例。`OVERGROWN_COLOSSUS_SERVANT` 原来也多带了 `.fireImmune()` 和 `sized(3.0F, 5.0F)`，2026-09-25 用户确认两项都无来由，已改回 `.sized(2.0F, 2.6F)` 并去掉火免（LM `overgrown_colossus` = `.sized(2.0f, 2.6f)`、不火免；模型几何与 LM 逐字节相同、两边渲染器都无缩放，5.0 的高度是从 `annihilation_pursuer` 的 `1.5F, 5.0F` 抄错）。
