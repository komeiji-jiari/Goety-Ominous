`Leapkelp`(潮涌之叶)2026-09 加的跳跃功能。几个踩过才知道的点:

**0. 2026-10-03 改动(用户要求"删除跳跃入水和出水,改成正常上岸和下水")**:上/下水两个大跳 goal(`LeapkelpLeapAshoreGoal` / `LeapkelpLeapIntoWaterGoal`)连同它们的基类 `LeapkelpLeapGoal`、退避(`leapRetryTick`)、落点扫描(`findLeapTarget`/`findColumnSpot`/`isWaterLeapSpot`/`isGroundLeapSpot`/`leapBox`)、速度反解(`leapSpeedTo`/`leapLaunchDrag`)全删。**下水**:本来就有的 `LeapkelpGoToWaterGoal`(原版 `DrownedGoToWaterGoal` 移植)自己会走过去,不需要额外东西。**上岸**:照抄原版 `Drowned.DrownedGoToBeachGoal`(extends `MoveToBlockGoal(mob, speed, 8, 2)`),落在 priority 3 —— 找附近"可站立 + 上方 2 格空"的陆地方块,然后**用陆行导航走过去**。它同时把上面第 3/11 条那套"泳动 MoveControl 不会跳"的死结解开了,而且不需要任何跳跃代码:关键在 `wantsToSwim()` 里新增 `if (wantsToLeaveWater()) return false;`,于是离水时 `travel()` 落到原版 water 分支(有重力/16、有横向 `horizontalCollision` + 0.6 净空 → `+0.3 y` 的爬台),`MoveControl` 落到 `super.tick()`(它的 MOVE_TO jump 在水里等于 `jumpInFluid` = 上浮,靠这个甚至能从深水里升上来爬岸)。**⚠️ 这一条 2026-10-03 被推翻**:那个"原版 jump 当上浮用"的设计就是"在水里悬着一直跳、还不前进"的病根(原版 `Operation.JUMPING` 会把 `zza` 清零),已改成 MoveControl 只按 `isInWater()` 分支、水中绝不落到原版,详见 [[goety-amphibious-floatgoal-bounce]] 第 2 来源。**代价待实测**:爬岸的"上升"以前有一部分就靠这个 jump,现在改由泳姿的 `yya`(朝向目标俯仰)+`searchingForLand` 的 `+0.002` 浮力提供,能不能照样爬出岸要进游戏确认。注意 **目标方块取 `pos.above()`**(`MoveToBlockGoal` 自己就是这么干的),wantedY 比脚下高 → `d2 > maxUpStep` 正好触发 jump。踩到的坑:原版 `MoveToBlockGoal` 每评估一次 canUse 就写 200~400 tick 的 `nextStartTick` 冷却 → 覆写 `nextStartTick` 到 20~40;goal 本身要自己加 6s 超时 + `canContinueToUse` 里复查 `isInWater() && wantsToLeaveWater()`(否则怪上了岸还抱着 MOVE 旗子站桩,卡死跟随)。跳劈(`LeapkelpLeapAttackGoal`)与它依赖的入水沉降/动画倍速当时保留——**但同日(2026-10-03)水中战斗改成"只留勾拳"时也整条删了**,详见 [[leapkelp-swim-anim-coralssus-port]];下面第 8/11/13 条描述的就是那套已删代码,留作「踩过的坑」备查,别当现存实现读。

**1. 自己 `setLeaping(true)` 就得自己复位。** `isLeaping()` 只在 `Leapleaf$LeapGoal.tick()` 落地分支里被清(`onGround() && leapTick > 1`)。外部 goal 起跳后若不复位,生物永久非碰撞(`canCollideWith`/`push`/`doPush` 全被 `isLeaping` 关掉)、ATK/KB 修正常驻。复位要连带 `leapTick = 0` + 给 `coolTick`(它单向递减,同时是 `LeapGoal`/`StrafeGoal` 的闸)。

**2. 起跳期间必须双保险绕开自研泳动。** `Leapkelp.travel()` 的 swim 分支是 `moveRelative(0.01F)+move+scale(0.9)` **且完全没有重力** → 施加的跳跃冲量会变成"匀速上飘"几十格。同时 `LeapkelpMoveControl.tick()` 的 swim 分支每 tick 用 `setSpeed/setZza/setYya` 覆盖输入,会跟冲量抢。所以两处都要 `isLeaping()` 门控(goal 里再每 tick `navigation.stop()`)。冲量时机照抄上游:在 `leapTick > 0` 那一 tick 一次性 `setDeltaMovement`(上游是 `== 1`)。注意 `Leapleaf.tick()` 是**先 `super.tick()`(goal 选择器在里面)再 `++leapTick`**,所以 goal 看到的是本 tick 自增前的值:`start()` 里 `setLeaping(true)` 当 tick 看不到 `leapTick > 0`,下一 tick 才施加冲量,与上游 `leapTick == 1` 同一时刻。

**3.(旧方案,上/下水跳已删)** "上岸"卡死的根因不是路径。** 水态用的是 `ModWaterPathNavigation`(AmphibiousNodeEvaluator,能规划出通向陆地的路径),但泳动 MoveControl 只会俯仰前进、不会跳 → 贴在岸边推墙。所以只需要"靠近岸时跳一下",不需要改导航。

**4. 两个方向都要 `!needsWater()` 门控。** `needsWater()` = 湿度 < 4000 **或** 主人+跟随+主人在水里。若只按"主人在岸上就跳上岸",会与"渴了就跳下水"形成 0.5s 一次的来回弹。现在的取舍:渴了老实待水里(水里 +2/tick 回湿,约 100s 回到 4000),不渴才跟随上岸。

**5. 优先级按 [[goety-servant-goal-priority-flags]] 的规则选**:`WrappedGoal.canBeReplacedBy` = `interruptable && candidate.priority < running.priority`(严格小于)。上岸压 `FollowOwnerGoal(5)`/`SwimUpGoal(6)`/`WaterWanderGoal(7)` → 放 3;下水压 `GoToWaterGoal(3)` → 放 2。**同号不会互抢**(2 压不动 2),所以同号的胜负由 `GoalSelector.availableGoals` 的 LinkedHashSet 插入顺序决定(super 先注册的先评估、先锁 flag)。(当时那条水中攻击跳就是靠"放在 2 + 注册在后 + `onGround` 与上游 LeapGoal 天然互斥"分工的;该 goal 已删。)

**6.(已删,见第 0 条)** 落点判定**用 `level.noCollision(mob, 当前 AABB 平移过去)`(标准做法)+ 岸上要求"脚下实心、本格无水无碰撞、上方 2 格净空",水里要求"本格是水、本体与上方非实心"。取样是"距离 2..5 递增 × ±90° 抖角度"。跳歪了会落回水里 → `leapRetryTick` 退避(20→40→…→200 tick,成功清零)重试,所以不需要精确抛物线。

**7. 客户端姿态是"混合"的,不是二选一**。先记住原版语义:`KeyframeAnimations` 的 `Targets.*.apply` 是**加法**(所以 `applyStatic(SWIM_POSE)` 之后再 `animateWalk(SWIM)` 能叠加,`resetPose()` 是每帧的基线)。`LeapkelpModel` 原来用布尔 `inWater = isInWater() && !isLeaping() && !isCharging()` 二选一基姿 → 落水/起跳时整套基姿一帧内突变(观感就是"落地接不上泳姿")。现在用 `Leapkelp.swimPoseAmount`(0..1,两端各每 tick 算一次,`Mth.approach(..., 0.15F)`,约 7 tick 走完)驱动:小于 1 先摆陆姿(IDLE/WALK)并 `captureLandPose()` 快照(rot + pos 共 6 个 float,`IdentityHashMap<ModelPart, float[]>` 按 part 存,每次全覆盖写所以模型单例共享没问题);大于 0 再 `resetPose` 后摆泳姿(SWIM_POSE/SWIM);0 与 1 之间逐骨骼 `Mth.lerp` 回插。这样双向都平滑(落水进泳姿、水里起跳回陆姿)。帧间插值:`getSwimPoseAmount(partialTicks)` = `Mth.lerp(partialTicks, 上一 tick 值, 本 tick 值)`,partialTicks 由 `ageInTicks - entity.tickCount` 反推(renderer 传的 ageInTicks = tickCount + partialTicks)。目标值仍是 `isInWater() && !isLeaping() && !isCharging()`,跳/蓄力期间照样走陆姿。`swimPoseAmount` 刻意不做 SynchedEntityData:两端各自算,客户端有实体实例和同步过的 isLeaping/isCharging,和原版 `swimAmount` 一个套路。

**8.(已删,见第 0 条)水里"跳跃技能"没有走 mixin,而是照抄上游 `LeapGoal` 的 charge→leap→smash 三段时间线另写了一个 goal**。原因:`Leapleaf$LeapGoal` 是包私有静态嵌套类,`canUse` 的 `onGround()` 与 `tick` 里落地分支的 `onGround()` 两处都要改,后者是复合条件里的一个表达式(要 MixinExtras `@ModifyExpressionValue` 且 INVOKE 的 owner 是 `Leapleaf` 不是 `Entity`,易碎);而且用户此前主动撤掉过那版 `LeapleafLeapGoalMixin`。自研版的"技能频率一致"= 同 `CHARGE_TICKS 24`(1.21s)+ 落地 `coolTick = 40`(2s)+ 命中 `restTick = REST_TIME`(潮涌之叶在 `tick()` 里截到 20)。冲量用上游原值 `(dir*0.6, 0.75 + clamp(dy*0.05,0,0.5))`。水的终止条件不能用 `onGround()`:改成 `onGround() || (isInWater() && 水平速度² < 0.02)`(水里 drag 0.8,约 7 tick 把 0.6 衰减到 0.14 以下)+ 40 tick 超时兜底。伤害/击退继承 `isLeaping` 的 1.25×/2.0 加成(所以 `smash()` 要在 `setLeaping(false)` **之前**调,和上游同序)。粒子不能照搬:水里 `BlockParticleOption(ParticleTypes.BLOCK, 水方块state)` 会出问题,水里只发 `SmashParticleOption`(颜色取自方块的 mapColor,0 兜底 `ColorUtil.WHITE`)+ `ParticleTypes.SPLASH`。**冲击波环的 y 别照抄上游**:上游是 `BlockFinder.moveDownToGround(entity)`,它往下找第一个**实心**方块(水不算),水里于是把环发到水底去了;水里要换成 `this.getY()`(身体位置),只有陆地上才用 `moveDownToGround`。goals 用 `MOVE+JUMP` 两个 flag(和上游一样),蓄力期间锁住 MOVE → 泳动追击/跟随/游荡全让位。

**9. 上游 `LeapGoal` 的落地判定只认 `onGround()` → 跳进深水 = 永久 `isLeaping`**(非碰撞 + MoveControl 冻结 + `travel()` 永久走 `super.travel()` + 属性修正常驻)。触发很现实:岸上(onGround)对水里目标起跳、或蓄力时被推下水。它唯一的清理由 `stop()` 提供,而 `canContinueToUse` 是 `target != null && (isCharging()||isLeaping())` → 只要目标还活着、生物又永远落不了地,就永不 stop。兜底:`Leapkelp.tick()` 里 `isLeaping() && leapTick > 80` → 清 isLeaping + 给 10 tick cooldown(给 cooldown 是为了不让上游 goal 下一 tick 立刻再跳)。

**10. 上游 `LeapGoal.stop()` 不清 `isCharging()`,而 `start()` 里是 `setCharging(!isCharging())` 的翻转写法**——所以蓄力期间目标死亡/被清 → goal 停 → charging 永远为真。陆地上能自愈(下一次 start 翻转成 false,goal 因 `canContinueToUse` 为假立刻停,再来一次就真蓄力了),**水里因为 `canUse` 要求 onGround 而无法自愈** → 永久 charging → `LeapkelpSwimAttackGoal.canSwimToTarget()` 的 `!isCharging()`、`AttackGoal`(SMASH)的 `!isCharging()` 全被永久掐死(只有泳姿在动)。兜底:`Leapkelp.tick()` 里 `isCharging() && chargeTick >= 24 && getRunningGoals().noneMatch(g -> g.getFlags().contains(Goal.Flag.JUMP))` → 清 charging。**必须带 JUMP 那半句**:上游追击 >6.5 格的目标时是"chargeTick 顶到 2s 上限还继续蓄力 + navigation.moveTo 靠近",那时 goal 正持 JUMP flag,不能误清(误清会让 2s 一次的 CHARGE 动画/音效重播)。

**11.(已删,见第 0 条)水里"落地不自然"的根因是三个同时发生的事**:(a) 入水那一 tick 原速穿入,而自研 swim 分支无重力 + drag 0.9 → 变成匀速长距离下滑;(b) 落地判定一满足立刻 `setLeaping(false)` → MoveControl 同 tick 解冻、模型同 tick 从陆姿突变成 SWIM_POSE,和入水水花撞在同一帧;(c) 水花粒子发在 `smash()` 时刻。修法:`Leapkelp.tick()` **顶部(`super.tick()` 之前)**调 `tickLeapWaterLanding()`(放前面 goal 才能看到本 tick 的判定,放后面会差 1 tick)。用 `leapAirborne` 记"这一跳出过水",重新入水那一 tick 做:速度 `multiply(0.4, 0.2, 0.4)` 当入水阻力 + `getSwimSplashSound()` + `sendParticles(SPLASH/BUBBLE)`(**服务端 `Level.addParticle` 是空操作,`doWaterSplashEffect()` 在服务端只有声音没有粒子**,粒子必须自己 `sendParticles`)+ `leapWaterSettleTick = 6`。沉降这 6 tick 里 `isLeaping()` 保持为真 → 陆姿 + MoveControl 冻结多留 0.3s,等身体停住再切泳姿,把"姿态突变"和"入水"错开。计时走完 `isLeapWaterLandingDone()` 才是 goal 的结束条件。全程没出过水的水下冲刺(深水里目标也在水里)走老判定"水平速度² < 0.02",不放入水水花。状态复位只能挂在覆写的 `setLeaping(true)` 上——上游 `LeapGoal` 也会 `setLeaping(true)`,那是唯一能覆盖所有起跳来源的钩子。顺带修掉一个老毛病:上岸跳失败落回水里 / 下水跳全程没出水时,原来要熬满 `LEAP_TIMEOUT_TICKS`(60)才结束,那 3 秒里生物在 `isLeaping` 下走 `super.travel()` 匀速下沉,现在入水沉降一结束就停。代价:水里一次循环比陆地多约 6 tick(沉降),陆地仍是 24 蓄力 + 40 cooldown 不变。

**12.(已删,见第 0 条;`leapSpeedTo` 已随跳劈一并删除)起跳水平速度必须按真实逐 tick 物理反解,不能拍系数**(2026-09 修"从岸上跳到岸上"= "差点跳进水里结果落到陆地")。原写法 `水平距离 × 0.14` 恒定欠射 0.6~2.05 格,根因是**冲量那一 tick 是地面 tick**:`LivingEntity.travel` 的 `f4 = onGround() ? 摩擦×0.91 : 0.91` 在这一 tick 就按 0.6×0.91=0.546 衰减(不是 0.91),有效横向倍率因此是 ~4.9 而不是 ~~7.5~~。现在 `leapSpeedTo(horizontal, dy, lift, tailTicks)` 先模拟弧线拿到落点 tick,再累加位移序列 `1 + Σ launchDrag×0.91^i` 反解速度,误差 0(验证脚本 `.scratch/leap_arc_check.mjs` 逐格复算:tick 与落点距离全对齐)。两个坑:(a) 首 tick 衰减要看起跳状态——**下水跳从陆地起(`onGround`→摩擦×0.91)**,**上岸跳从水里起(`!onGround`→0.91;实际走水分支的 0.8 slowDown,偏乐观=略欠射,落在岸边方向,可接受)**;(b) `leapAirTicks` 判"落到目标高度"的 tick 只在**过顶点之后**接受 `height <= dy`(`else if` 挂在 `height > apexHeight` 后面),否则向上去的目标(岸上 +2/+3 格)会在上升段就返回 tick 1 → 速度被顶到上限、动画倍速 4.3×。

**13.(已删,见第 0 条)LEAP 动画 1.5s(30 tick)比实际滞空长得多 → 用同步倍速补完,不要让它被截断**。我们的跳滞空只有 11~22 tick(旧弧线 ~11 tick),跳跃结束 → 服务端 `setAnimationState(IDLE)` → 客户端 `stopMostAnimation` 直接 `AnimationState.stop()`,模型停在翻滚中段硬切回站姿,观感就是"动画播一半停止"。上游自己也截断(它的跳 ~17 tick),所以别指望靠"跳久点"解决(要 30 tick 滞空得抬升 7 格)。做法:`SynchedEntityData` 加 `LEAP_ANIM_SPEED`(int,百分数,两端各算不了必须同步——客户端不知道弧线),`leapSpeedTo`/`alignLeapAnimSpeed` 按 `30 / (滞空 tick + tail)` 写入(实测 0.97~1.76×),`LeapkelpModel` 用 `animate(state, def, ageInTicks, entity.getLeapAnimSpeed())`(4 参重载,1.20.1 是 `updateTime(age, speed)` 只缩放增量,相位不会跳),`setLeaping(false)` 里复位成 1.0(上游 `LeapGoal` 的跳不受影响)。Water 跳 tail = 沉降 6 + 3,陆地/攻击跳 = 3。

**14.(已删,见第 0 条)** 两个方向的跳都要上报结果**。原来只有上岸跳 `recordAshoreLeap(!isInWater())`,下水跳失败(落回陆地)不留退避 → 10 tick 冷却一到就再跳,一次失败会变成连着蹦。现已统一成 `recordLeapResult(success)`:上岸跳 success = `!isInWater()`,下水跳 success = `isInWater()`,失败按 20→40→…→200 tick 退避。

**16. 2026-10-03 晚「沉底行走被卡住」= 水里挂着陆行导航 + `getStepHeight()` 恰好 1.0f。**

- **导航不能跟着 `wantsToSwim()` 一起切。** 原 `updateSwimming()` 是 `isInWater() && wantsToSwim()` 才用 `waterNavigation`,于是"主人上岸 → `wantsToLeaveWater()` → `wantsToSwim()` false"时,怪**在水里却挂着 `GroundPathNavigatorFat`**。它是纯 `WalkNodeEvaluator`(非两栖):`WalkNodeEvaluator.java:251` 对 `!isAmphibious() && WATER && !canFloat()` 把水节点判死,起点只能吸附到别处 → 规划出的是**贴底面**的陆路(旧日志实证:怪 y=60.8,`0/16@-58,57,-101`,首节点在海底 3.5 格下)。表现:该游泳的怪**在海底行走**、被海底地形磨住。**修法**:`updateSwimming()` 只按 `isInWater()` 选导航(水里恒 `waterNavigation`),`setSwimming` 继续跟 `wantsToSwim()` —— movement 模式不变,离水照样落 `super.travel()`。
- 第 0 条那套"照抄溺尸 `DrownedGoToBeachGoal` + 陆行导航走过去"对**大体型**不成立:溺尸 bbWidth 0.6,贴底步进跟得上;我们 1.9 宽 + 海底台阶密,贴底必然卡,而且水里用陆行导航本来就规划不出水路。
- **`getStepHeight()` 是第二个坑**:Goety `Leapleaf` 返回**恰好 `1.0f`**,而 `AmphibiousNodeEvaluator`/`WalkNodeEvaluator` 生成邻居时按 `Mth.floor(Math.max(1.0F, stepHeight))` = **1 格**当作可跨 → 寻路认为能上、移动侧却卡在 1.0 的边界(FP 一偏就差那一点)。已覆写 `getStepHeight() = Math.max(1.25F, super.getStepHeight())`(保留 `forge:step_height` 属性加成;`floor(1.25)=1` 所以寻路行为不变)。详见 [[forge-maxupstep-mapping]]。
- 配套:水中 MoveControl 补的原版"台阶高了就 jump"那段见 [[vanilla-swim-movecontrol-xxa-reference]] 第 8 条 —— 那是**出水/跨 2 格坎**用的,1 格坎归 `getStepHeight()` 管。**⚠️ 该段 2026-10-06 已重写**(那两半条件一个贴海底就触发、一个是 +0.3 无重力累积 → 高速上升飞出水面),修法与理由见同文件第 9 条。

**15. 2026-10-03 晚「水面要陆地站立态、可以跳」= 珊瑚巨像的 `swim` 判据 + 一个补集门的新 `LeapkelpSurfaceLeapGoal`。**

- **站立判据照抄珊瑚巨像**(`CoralssusServant.tick:524-531`):`swim = 眼睛在可游泳流体里 && level().noCollision(this, getBoundingBox())`。我们用 `isSwimmingPose() = isInWater() && isEyeInFluidType(ForgeMod.WATER_TYPE.get()) && level().noCollision(this, getBoundingBox()) && !isLeaping() && !isCharging()`,`updateSwimPoseAmount()` 的目标值从原来的 `isInWater()` 换成它。两个副作用都是想要的:**眼睛露出水面 → 陆姿**;**浅水踩底(bbox 与地面方块相交 → `noCollision` 假)→ 也是陆姿**(`BlockCollisions` 会把 AABB inflate 1e-7,贴着脚底的方块算碰撞,正好当"站在地上"用)。两端各算,不进 SynchedEntityData(同第 7 条)。`isVisuallySwimming` 那半边**没动** —— 1.20.1 的 `LivingEntityRenderer.setupRotations` 不读 swimAmount,它只喂 `updateSwimAmount`,而我们的模型用的是自己的 `getSwimPoseAmount`。
- **新 goal 的 `canUse` = 上游 `LeapGoal` 的补集**:`coolTick`/`onGround` 换成 `isInWater() && !isSwimmingPose() && !onGround()`(水里浮着、眼出水、没踩底)+ `canAttack`。其余(24 tick 蓄力 → 距离 ≤6.5 起跳 → 冲量 `(dir*0.6, 0.75+clamp(dy*0.05,0,0.5))` → 落地)逐行复刻上游,动画/音效沿用 `CHARGE`/`LEAP` + `LEAPLEAF_CHARGE`/`LEAPLEAF_LEAP`。与上游陆地 `LeapGoal` 同优先级 2、同 flag,靠 `onGround` 互斥分工,不删上游那个。
- **落地判定不能用 `onGround()`**:水里 `isLeaping()` 期间 `travel` 落回 `super.travel`(原版水分支,`y*0.8`),0.75 的上冲能顶出水面 >2 格,出水后接空气弧线;判定写成 `leapTick > 10 && (onGround() || isInWater())`。**这个 10 tick 门槛是必需的** —— 起跳瞬间生物还在水里,不做延时判定会当 tick 就"落地"把跳掐掉。
- **这招不能共用上游 `coolTick` 做冷却**:水里离底时我们 `coolTick = 0`(封 `StrafeGoal`,见 [[vanilla-swim-movecontrol-xxa-reference]]),拿它当冷却等于没有。改成实体字段 `surfaceLeapCooldown`(40 tick,在 `Leapkelp.tick()` 里递减——**不能放 goal 自己的 `tick()`**,goal 没在跑时不被调用,冷却会永远卡住)。
- 落地效果照上游(附近敌人按 25% 概率吃 `restTick = REST_TIME`,我们截到 20 tick;**上游这招落地不做伤害** —— 伤害在后手:陆上 SMASH / 水里左右重砸),只有左/右两处方块碎片环换成水里那套 `SmashParticleOption` + `SPLASH` + `CameraShake`(方块粒子在水里不可见,同本文件第 8 条)。
- **1.20.1 的 `GoalSelector` 不按 priority 排序**:`availableGoals` 是 `LinkedHashSet`,插入序评估,priority 只通过 `WrappedGoal.canBeReplacedBy`(`interruptable && candidate.priority < running.priority`,严格小于)在抢 flag 时起作用。所以同优先级 = 先注册的(上游 super 那批)先评估先锁 flag。
